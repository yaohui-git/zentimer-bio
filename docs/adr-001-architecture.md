# ADR-001 · 架构纠正：为什么独立伴侣页，而不是改 zentimer 主 App

- **状态**：已采纳（2026-11-13）
- **取代**：v0.1 首版方案（2026-11-13，基于「纯前端 Web App」的错误假设，已整体废弃，内容不再保留）
- **决策者**：项目所有者（耀慧）确认前四项前提，本 ADR 由工程侧提出

## 背景：v0.1 的前提判断错了

v0.1 依据「同名仓库搜索结果」推断 Zen Timer 是**纯前端 Web App（HTML/JS + localStorage）**，因此设计成「浏览器 Web Bluetooth 插件直接嵌进 Zen Timer」。

读取真实仓库 [`yaohui-git/zentimer`](https://github.com/yaohui-git/zentimer) 后发现：

| 维度 | v0.1 假设 | 实际情况 |
|---|---|---|
| 形态 | 浏览器 Web App | **Android 原生 App**（Kotlin 2.2.10 + Jetpack Compose，Gradle 单模块，单 Activity） |
| 网络 | 可有可无 | **完全离线，manifest 里根本没有 `INTERNET` 权限** |
| 权限 | 不涉及 | 只申请 1 项通知权限；另有可选的勿扰特殊权限，**默认关闭** |
| 数据存储 | localStorage | SharedPreferences（语言/主题/预设） |
| 练习记录 | 有历史记录 | **明确没有统计、练习记录、账号、社区、推送、信息流** |
| 许可证 | 未知 | 代码 **Apache-2.0**；随包 23 段音频 + 36 张图片是第三方资产，**不在协议内**（见其 `NOTICE.md` / `ASSETS-NOTICE.md`） |
| 产品底线 | 未考虑 | 「一屏一只圆环」「留白、不打扰」「离线、不多申请权限、无广告」，定制版也守住这三条 |

结论：**「往 Zen Timer 里加一个 Web Bluetooth 插件」在技术上不成立**——它是原生 App，没有 WebView、不跑 JS、无网络权限。v0.1 的第 4 节对接方式整体作废。

## 决策

### D1 · v1 完全不改动 `zentimer` 主仓库，新建独立仓库 `zentimer-bio`

理由：

- 给它加 BLE 需要在 Android 12+ 声明 `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT`，权限清单从 7 项变 9 项，**直接打破「只申请一项通知权限」这一核心承诺**，隐私政策、商店素材、README 全部要重写。
- 主 App 刻意「没有练习记录/统计」，把生理数据与会话历史塞进去等于改变产品定义。
- 项目所有者已明确「这个项目建新库：`zentimer-bio`」。

**代价**：用户要同时打开两个东西（主 App 负责计时与钵声，伴侣页负责监控/分析/指导）。但这与「不打扰」哲学相容——伴侣页默认静默采集，坐完再看报告，冥想过程中不弹窗、不出声。

**未来可选（不在 v1）**：若项目所有者日后愿意在主 App 里做「可选 bio 模块」，需要单独评估权限与隐私政策变更；本仓库的协议层已按可复用设计，届时可移植。**本 ADR 不授权改动主仓库。**

### D2 · 伴侣层 = 纯前端网页，无构建、无依赖、`file://` 可直接打开

`web/zenbio.js` + `web/index.html` + `web/report.html`。所有视觉用 CSS/SVG **自绘**，绝不复用主仓库的音频/图片素材（那些是第三方资产，不在 Apache-2.0 内）。

会话数据存在伴侣页的 `localStorage`（后续可换 IndexedDB），不写进主 App 的 SharedPreferences。

### D3 · 主通道 = ESP32 AP 热点 + WebSocket；辅通道 = Web Bluetooth

| | AP + WebSocket（主） | Web Bluetooth（辅） |
|---|---|---|
| 页面托管 | **ESP32 自己托管** `http://192.168.4.1` | GitHub Pages（HTTPS）或本地文件 |
| 是否需要外网 | **不需要，完全离线自持** | 需要 |
| 是否需要 HTTPS | 否 | 是 |
| 浏览器要求 | **所有浏览器都支持普通 HTTP/WS** | Chrome / Edge / 安卓 Chrome；Firefox、Safari、iOS 全系不支持 |
| 用途 | 指夹日常使用、最贴合主 App 的离线气质 | 桌面调试、接第三方标准 BLE 心率带 |

项目所有者明确「不管 iOS 先」，所以**不做 iOS 原生 App、不申请 Apple 开发者账号**。但 AP 通道顺带把 iOS/Firefox 的兼容问题一并解决了，成本为零，因此列为主通道。

功耗取舍（阶段 1 一律 USB 供电，不存在该问题）：BLE 约 30–60 mA，WiFi AP 约 120–200 mA；阶段 2 电池版默认 BLE，需要离线自持时切 AP。

### D4 · 时间对齐靠手动，v1 不做自动同步

流程：先在「静息」里选时长、听一声钵开始静坐 → 回到伴侣页点「开始记录」→ 结束后写自评。

理由：主 App 没有任何对外 IPC / 广播接口，且我们承诺不改它。自动同步需要主仓库配合，属于 D1 的「未来可选」。

### D5 · 小米手环 3 / 4 不作为 HRV 数据源

核实结论：

- 规格上**不支持 HRV**，只提供瞬时心率；
- BLE 走华米私有协议（`fee0` / `0009` 认证挑战 + AES），社区项目读心率靠「运动心率广播」抓广播包或写 `0x2A39` 控制点触发单次测量；
- **不提供标准 RR 间期流**，而 HRV（RMSSD / SDNN / 0.1 Hz 相干性）必须基于逐拍 RR 间期。小米手环 3 虽暴露 `0x180D`，但广播的是心率值而非 RR 序列。

因此两只小米手环的正确用法是：**作为瞬时心率的对照参考**（验证自研指夹的 HR 读数是否离谱），以及通过 Zepp Life 看长期趋势，**不参与 HRV 计算**。

**替代方案（项目所有者已确认「时间和成本都没问题，有公司报销」）**：补一条标准 BLE 心率带，广播 `0x180D` 且带 RR 间期，可直接用 Web Bluetooth 在阶段 0 做出真实 HRV，并作为整个项目的**校准金标准**：

| 型号 | 参考价 | 说明 |
|---|---|---|
| Magene H64 / CooSpo H808S | ¥140–260 | 够用，支持 BLE + ANT+、RR 间期 |
| **Polar H9（推荐）** | 约 ¥498 | 性价比高的参考级，研究文献常用同门 H10 作金标准 |
| Polar H10 | ¥600–750 | 实验室级 RR 精度，有预算可直接上 |

> 这是「有报销」最值得花的一笔钱：**花在测量基准上，而不是提前买 EEG**。它让阶段 0 从「纯模拟」升级为「真实数据」，也让后续所有算法调参有可对照的尺子。

### D6 · 许可证矩阵（按真实主仓库许可修正）

| 资产 | 协议 | 说明 |
|---|---|---|
| 固件 / 伴侣页 / 工具脚本 | **Apache-2.0** | 与 `zentimer` 主仓库一致，便于未来代码复用或合并，无 GPL 兼容问题 |
| 原理图 / PCB / 结构 / BOM | **CERN-OHL-S-2.0** | 硬件专用、OSI 认可、强互惠；若希望被商业产品集成改 `-W-2.0` |
| 文档 / 教程 | CC-BY-4.0 | CERN 官方对文档的推荐 |
| 示例数据 | CC0-1.0 | 方便他人无顾虑用于研究 |
| 商标 / 项目名 | 保留 | 不随开源许可授予 |

**严禁**把主仓库的 `res/raw/` 音频、`res/drawable-nodpi/` 图片、启动图标人形剪影搬进本仓库。

### D7 · 形态与合规定位（沿用 v0.1，已确认）

- 起步形态：**指夹**（项目所有者确认），PPG 信号最好、最便宜、最不打扰。
- **不是医疗器械**，不用于诊断治疗，不做「改善焦虑/抑郁/失眠」等疗效宣称。
- 不照搬「LF/HF 高 = 压力大」：约 6 次/分共振呼吸时 LF 功率刻意升高，那是训练目标。主指标为 RMSSD / 0.1 Hz 相干性 / 静稳度。
- **主观自评必填**：没有主观标注，生理数据不构成「效果」标签。

## 后果

| 正面 | 负面 / 风险 |
|---|---|
| 主 App 的产品灵魂（离线、极简、不多申请权限）完整保留 | 用户要操作两个界面；时间靠手动对齐 |
| 伴侣页零构建、全平台、完全离线自持 | AP 模式功耗高，电池版需模式切换 |
| 真实 HRV 基准可在阶段 0 就拿到 | 需额外采购一条心率带（已确认可报销） |
| 协议层与适配器解耦，未来可移植进原生模块 | 主 App 集成需另开 ADR，不在本期 |
| 不触碰第三方素材，版权干净 | 视觉需全部自绘（已完成） |
